# Data Quality Checks Report

This document summarizes the data quality checks performed across the **Bronze**, **Silver**, and **Gold** layers of the data warehouse, the issues discovered, their root causes, and the solutions applied — whether the fix was made directly on the **source CSV file**, through transformation logic in the `silver.load_silver` stored procedure (**Bronze → Silver**), or through integration/modeling decisions in the **Gold layer** (**Silver → Gold**).

---

## 1. Bronze Layer

### 1.1 Missing Last Record — `bronze.erp_cust_az12`

| | |
|---|---|
| **Issue** | Row count after loading (`18,483`) did not match the expected row count from the source CSV (`18,484`). |
| **Investigation** | Queried the last expected record (`cid = 'AW00029483'`) directly in the Bronze table and confirmed it was missing. |
| **Root Cause** | The source CSV file was missing a trailing newline character at the end of the file, causing `BULK INSERT` to fail to recognize the last data row. |
| **Solution** | Added a newline character to the end of the source CSV file. |
| **Where Applied** | ✅ **Fixed at the source CSV file**, before the Bronze load. |
| **Validation** | Row count after reload matched the source file exactly: `18,484` records in both source and Bronze. |

## 2. Silver Layer — Issues Found During Bronze Quality Checks & Their Implementation

The following issues were identified while validating Bronze tables. All of them have now been resolved through transformation logic implemented in the `silver.load_silver` stored procedure, which truncates each Silver table and reloads it with cleansed data from the corresponding Bronze table.

### 2.1 `crm_cust_info`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| Duplicate / NULL primary keys | ~6 duplicate `cst_id` values and 3 NULLs found. Investigation showed duplicates differed by `cst_create_date`. | Kept only the most recent record per `cst_id` using `ROW_NUMBER() OVER (PARTITION BY cst_id ORDER BY cst_create_date DESC)`, filtering to `flag_last = 1`; records with `cst_id IS NULL` are excluded up front. | Silver ✅ |
| Unwanted spaces | Leading/trailing spaces found in `cst_firstname` and `cst_lastname`. | Applied `TRIM()` to both columns. | Silver ✅ |
| Inconsistent codes | `cst_marital_status` used `S` / `M`; `cst_gndr` used `M` / `F`, with `M` ambiguously meaning both "Married" and "Male". | Mapped via `CASE` on the uppercased/trimmed value: `S` → `Single`, `M` → `Married` for `cst_marital_status`; `M` → `Male`, `F` → `Female` for `cst_gndr`. Any unrecognized or missing value defaults to `N/A`. | Silver ✅ |

### 2.2 `crm_prd_info`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| Category code embedded in key | `prd_key` contains a category code that should map to `id` in `erp_px_cat_g1v2`. | Split into two columns: `cat_id` = `REPLACE(SUBSTRING(prd_key, 1, 5), '-', '_')` and `prd_key` = `SUBSTRING(prd_key, 7, LEN(prd_key))`. | Silver ✅ |
| Duplicate / NULL `prd_key` | Duplicates and NULLs found in `prd_key`. | Resolved implicitly by the key-splitting logic above; no separate deduplication step was needed in the final version (an earlier `ROW_NUMBER()`-based dedup approach was tried and left commented out in the procedure for reference). | Silver ✅ |
| NULL product cost | NULL values found in `prd_cost`. | Replaced NULLs with `0` using `ISNULL(prd_cost, 0)`. | Silver ✅ |
| Inconsistent product line codes | `prd_line` stored as single-letter codes: `M`, `R`, `S`, `T`. | Mapped via `CASE` on the uppercased/trimmed value: `M` → `Mountain`, `R` → `Road`, `S` → `Other Sales`, `T` → `Touring`; unrecognized values default to `N/A`. | Silver ✅ |
| Invalid date order | Some records had `prd_start_dt > prd_end_dt`. | Recalculated `prd_end_dt` as one day before the next `prd_start_dt` for the same `prd_key`, using `DATEADD(DAY, -1, LEAD(prd_start_dt) OVER (PARTITION BY prd_key ORDER BY prd_start_dt))`. This is a data-enrichment step (the last record per `prd_key` naturally receives `NULL` as its end date, since there's no next start date to derive it from). | Silver ✅ |

### 2.3 `crm_sales_details`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| Integer-encoded dates | `sls_order_dt`, `sls_ship_dt`, `sls_due_dt` stored as integers in `YYYYMMDD` format, including invalid `0` values and values with length ≠ 8. | For each date column, a `CASE` sets the value to `NULL` when it equals `0` or its length ≠ 8; otherwise it's cast to `VARCHAR` and then to `DATE` (the two-step cast is required by SQL Server for integer-to-date conversion). | Silver ✅ |
| Missing order number | Some records had NULL `sls_ord_num`. | Filtered out with `WHERE sls_ord_num IS NOT NULL`. | Silver ✅ |
| Sales/Quantity/Price rule violations | Business rule `Sales = Quantity * Price` was violated in multiple records; NULL, negative, and zero values also found in `sls_sales` and `sls_price`. | If `sls_sales` is `NULL`, `≤ 0`, or doesn't equal `sls_quantity * ABS(sls_price)`, it's recalculated as `sls_quantity * ABS(sls_price)`; otherwise the original value is kept. If `sls_price` is `NULL` or `≤ 0`, it's derived as `sls_sales / NULLIF(sls_quantity, 0)`; otherwise the original value is kept. `sls_quantity` is trusted as-is (no negative/zero values were found for it). | Silver ✅ |

### 2.4 `erp_cust_az12`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| Foreign key mismatch (`cid`) | `cid` values prefixed with `NAS` did not match `cst_key` in `silver.crm_cust_info`. | Stripped the `NAS` prefix with `CASE WHEN cid LIKE 'NAS%' THEN SUBSTRING(cid, 4, LEN(cid)) ELSE cid END`. Verified zero unmatched records after the fix. | Silver ✅ |
| Out-of-range birth dates | Some `bdate` values were before `1924-01-01` or in the future (after `GETDATE()`). | Set to `NULL` when `bdate < '1924-01-01'` or `bdate > GETDATE()`, since ages beyond ~100 years or unborn customers are not realistic. | Silver ✅ |
| Inconsistent gender values | `gen` column contained `M`, `F`, `Male`, `Female`, `NULL`, and empty strings. | Mapped via `CASE` on the uppercased/trimmed value: `F` / `FEMALE` → `Female`, `M` / `MALE` → `Male`; anything else (including `NULL` and blanks) → `N/A`. | Silver ✅ |

### 2.5 `erp_loc_a101`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| Foreign key mismatch (`cid`) | `cid` contained `-` characters not present in `cst_key` from `crm_cust_info`. | Removed `-` characters using `REPLACE(cid, '-', '')`. | Silver ✅ |
| Inconsistent country values | `cntry` column mixed full country names and abbreviations (e.g., `DE` / `DEU` / `Germany`). | Mapped via `CASE` on the uppercased/trimmed value to full country names — `AU`/`AUS` → `Australia`, `CA`/`CAN` → `Canada`, `DE`/`DEU` → `Germany`, `FR`/`FRA` → `France`, `GB`/`UK` → `United Kingdom`, `US`/`USA` → `United States`. NULL or blank values map to `N/A`; any other value is kept as-is (trimmed). | Silver ✅ |

### 2.6 `erp_px_cat_g1v2`

| Issue | Details | Solution | Where Applied |
|---|---|---|---|
| None found | Checked for NULLs/unwanted spaces in `cat`, `subcat`, `maintenance`, and foreign key integrity against `cat_id` in `crm_prd_info`. | No action needed — table is already clean. | N/A |

## 3. Gold Layer — Views & Model Validation Checks

The Gold layer is implemented as a set of **views** (not physical tables) built directly on top of the Silver layer, forming a Star Schema: `gold.dim_customers`, `gold.dim_products`, and `gold.fact_sales`.

### 3.1 `gold.dim_customers`

| | |
|---|---|
| **Sources** | `silver.crm_cust_info` (base), `silver.erp_cust_az12` (birthdate + gender fallback), `silver.erp_loc_a101` (country) — all joined via `cst_key` / `cid`. |
| **Surrogate Key** | `customer_key = ROW_NUMBER() OVER (ORDER BY cst_id)`. |
| **Issue** | Gender information exists in two sources: `cst_gndr` (CRM) and `gen` (ERP), and their values don't always match for the same customer. |
| **Decision Needed** | Which source should be treated as the master when the two disagree? Confirmed with the source data expert: **CRM is the master source** for gender. |
| **Solution** | `CASE WHEN cst_gndr != 'n/a' THEN cst_gndr ELSE COALESCE(gen, 'n/a') END` — use CRM's value whenever populated; fall back to ERP's `gen` only when CRM is `n/a`. |
| **Where Applied** | Gold ✅ (`gold.dim_customers` view) |
| **Uniqueness Check** | `GROUP BY customer_key HAVING COUNT(*) > 1` → expected no results, confirming `customer_key` is a valid surrogate key for joining to `gold.fact_sales`. |

### 3.2 `gold.dim_products`

| | |
|---|---|
| **Sources** | `silver.crm_prd_info` (base), `silver.erp_px_cat_g1v2` (category/subcategory/maintenance) — joined via `cat_id` / `id`. |
| **Surrogate Key** | `product_key = ROW_NUMBER() OVER (ORDER BY prd_start_dt, prd_key)`. |
| **Filter** | `WHERE prd_end_dt IS NULL` — keeps only the **current, active** record for each product (the row with no end date), excluding historical/expired versions of a `prd_key`. |
| **Where Applied** | Gold ✅ (`gold.dim_products` view) |
| **Uniqueness Check** | `GROUP BY product_key HAVING COUNT(*) > 1` → expected no results. Since the view is already filtered to only active products (`prd_end_dt IS NULL`), each `prd_key` should surface as a single row here, so this check also implicitly confirms there isn't more than one "active" record left per product. |

### 3.3 `gold.fact_sales`

| | |
|---|---|
| **Sources** | `silver.crm_sales_details` (base), joined to `gold.dim_products` on `sls_prd_key = product_number`, and to `gold.dim_customers` on `sls_cust_id = customer_id`. |
| **Grain** | One row per sales order line, carrying the resolved `product_key` / `customer_key` surrogate keys instead of the raw business keys, plus order/shipping/due dates, sales amount, quantity, and price. |
| **Referential Integrity Checks** | `LEFT JOIN gold.dim_customers ON customer_key` → `WHERE customer_key IS NULL` (expected no results); `LEFT JOIN gold.dim_products ON product_key` → `WHERE product_key IS NULL` (expected no results). These confirm every sales row resolves to a valid customer and product in the dimensions. |

---

## 4. Design Note: `gold.dim_products` Keeps Only Current Products

`silver.crm_prd_info` can contain more than one historical row per `prd_key` (e.g., when a product record was re-created over time), each with its own `prd_start_dt` / `prd_end_dt`. In the Gold layer, this is intentionally simplified: `gold.dim_products` filters with `WHERE prd_end_dt IS NULL`, so **only the current/active version of each product** is exposed in the dimension, and `gold.fact_sales` joins to that single current record via `sls_prd_key = product_number`. Historical product versions are not modeled or exposed in the Gold layer.

All Gold-layer objects are implemented as **views** on top of Silver (`gold.dim_customers`, `gold.dim_products`, `gold.fact_sales`), so they always reflect the latest Silver data without needing a separate load step.

All Silver-layer fixes above are implemented in the `silver.load_silver` stored procedure, which truncates and reloads each Silver table from its corresponding Bronze table with the cleansing/transformation logic described. It can be executed with:

```sql
EXEC silver.load_silver;
```

The procedure wraps the full load in a `TRY...CATCH` block, printing per-table and total batch load durations, and re-throwing any error (with message, number, and state) if a step fails.
